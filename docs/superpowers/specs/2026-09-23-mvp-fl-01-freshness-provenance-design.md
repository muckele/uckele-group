# MVP-FL-01 — minimum durable freshness and provenance contract

**Status:** Proposed for owner review; design only. **Investigated code:** `fba00fd3579b49d64cc909dfc165a041604e600f`. **Integrated roadmap:** `18a8645845be5c77c7422e0d20a49fa6003bef1b` (PR #25 added only roadmap documents after the code baseline). **Date:** 2026-09-23. The local FL-00 trace is `docs/mvp-fl-01-freshness-contract-note.md` in the isolated worktree; it stays uncommitted.

## Decision and owner outcome

Give the existing Acquisition Inbox a defensible answer to **when UG first accepted evidence of this opportunity, when a source says it was published, when UG accepted the latest source observation, and whether decision-relevant evidence changed after the owner reviewed it**. Keep those facts separate from source export/modification times, score calculation, canonical identity creation, and owner action times. The data contract below is prerequisite to FL-01's labels and ordering. This document authorizes no runtime change, migration, import, outreach, repair, or deployment.

## Minimal stored contract

Use **two narrow new tables** because current source projections can be deleted and because concurrent collection needs a durable ordering watermark. Add bounded columns to existing tables; do not store raw CSVs or a full snapshot per run.

1. `deal_hunter_source_freshness_state` has one row per admitted source (`source_id` PK): `next_generation`, `accepted_generation`, `accepted_run_id`, `accepted_digest`, and `accepted_at`. Allocate a strictly increasing generation *before* fetching/processing through the server storage adapter. A failed run may leave a generation gap but changes no discovery or material history. An admitted transaction advances the accepted watermark only if its generation is newer. The same run ID and digest are idempotent; any older or conflicting generation fails closed. Deal OS import ID is the run identity; its later current projection is allowed only while its generation remains latest accepted, otherwise that projection is superseded. A Sheet collection gets a UUID run identity bound to its existing private admission. Source export/modification times are recorded separately and never used as this ordering token.
2. deal_hunter_freshness_evidence is an append-only, bounded event record. Types: accepted_source_record (each accepted Deal OS import row; for Sheet, first acceptance or changed value/provenance), publication_evidence, material_change, and evidence_state_change (new evidence, conflict, selected-source swap, disappearance). Common fields: immutable event ID, source ID/name, source-record identity, run ID/generation, database-assigned accepted_at, original canonical ID (nullable), identity-exception ID (nullable), current canonical ID (nullable one-time bind or approved reparent), provenance version, and event type. Publication fields retain bounded original header/value, meaning, normalized date or timestamp, precision (date/instant), offset/timezone, and invalid/future/conflict state. A material event retains field, typed before/after values and evidence IDs, classification, and canonical material revision. Unique (run_id, source_id, source_record_id, event_type, field, event_ordinal) makes retries idempotent; value hashes are not uniqueness keys, so A→B→A→B across distinct runs remains distinguishable. Original source association and event payload never change. Approved identity correction may update only current_canonical_id with an audit reference; it does not alter V3 receipts or source evidence.
3. Add to deal_hunter_opportunities: nullable first_accepted_at and first_discovery_evidence_id, discovery_state (untracked_legacy, pending, known_prospective, known_recovered), discovery_revision and material_revision (nonnegative, initially 0), and nullable last_material_change_at. Existing rows migrate to untracked_legacy with no first date; only identities created by the new guarded writer after cutover begin pending until accepted evidence binds. Rows created by old writers during schema-first rollout stay untracked_legacy. Discovery revision advances only when supported first-discovery proof binds or a proven correction changes it. known_recovered requires cited earlier retained evidence, not a processing date. A later import cannot promote an untracked_legacy row merely because it is first after rollout. Proven second-source matches and moved Sheet rows preserve earliest defensible date. If consolidation has incomplete earlier history, the first date remains unknown until resolved; never take a convenient minimum across uncertain owners.
4. Add to current deal_hunter_opportunity_source_observations: nullable accepted_at, accepted_run_id, and accepted_evidence_id, plus bounded publication-source header/raw value/precision/offset/meaning fields. accepted_at/run_id describe latest successful projection; accepted_evidence_id links retained evidence supporting the current value and may carry an older run ID after an unchanged refresh. Current rows remain replaceable; referenced evidence survives deletion. Add reviewed_discovery_revision and reviewed_material_revision (operator owned, initially 0 for previously reviewed score rows) to deal_hunter_opportunity_scores; never put them in machine score writes.

SQLite uses CHECK constraints, foreign keys where ownership is stable, guarded update triggers for immutable evidence, and an IMMEDIATE transaction. Postgres uses equivalent constraints, RLS, no public/anon/authenticated table privileges, and service-role-only SECURITY DEFINER RPCs with a fixed search path and source/canonical advisory locks. Keep admin queue/detail authorization unchanged. Index (current_canonical_id, accepted_at DESC, id), (source_id, source_record_id, accepted_at DESC), (run_id, source_id, source_record_id), and queue-supporting canonical columns; test query plans on representative synthetic volume. Events contain only bounded provenance/date/field values, never whole workbooks, messages, or documents. No-op Sheet refreshes update current accepted_at/run_id, retain accepted_evidence_id for the unchanged value, append no event, and advance neither revision. Each accepted Deal OS import row has a bounded acceptance event in its import transaction, even when its value is unchanged; that no-op appends no material/state-change event and advances neither revision. Discovery, supported publication changes, material transitions, and classified evidence-state changes remain for the canonical lifetime. Unreferenced no-op Deal OS acceptance events may be pruned only after identity is settled and a defined retention horizon, never while pending or cited by discovery, current observation, publication, review, or a transition. The per-source watermark avoids an unbounded run ledger; a retry below the watermark is rejected.

## Acceptance and write sequence

1. The existing collector/importer obtains a source run ID and database generation before work. It retains the source's export/modification times and the raw, bounded date header/value *before* `parseDate` discards precision. Only a verified source-specific mapping can interpret a field as **listing publication**. `Date Added`/`Created` remain `unknown meaning` unless that source's contract proves publication. A mere header spelling is insufficient. A date-only value stays a calendar date; an instant retains its offset. Malformed, missing, future, or contradictory dates carry explicit state and never receive a recency boost. Competing supported sources remain separately visible; no earliest/latest cherry-pick.
2. Keep current source-admission checks and canonical resolver. A rejected/failed Sheet collection or Deal OS row writes no accepted freshness event. Extend private complete Sheet admission to validate the fingerprint and exact set of all fetched source rows, including bounded unresolved-row evidence and identity-exception links, in one guarded SQLite transaction or service-role Postgres RPC. Do not weaken complete-scope proof. If any identity is unresolved, atomically accept bounded row evidence and exception links but defer the complete current-source projection: retain last-known current rows and show source scope as deferred/unhealthy. A provisional exception created before admission is not accepted evidence. No unresolved row receives a canonical first date. Later proven resolution binds the original event in the guarded identity transaction; a newer complete admitted collection can then replace current projection. Do not weaken matching. A preexisting canonical with unknown history stays unknown unless older retained evidence is proved.
3. Sheet and Deal OS have separate acceptance boundaries. Complete Sheet admission checks the generation watermark, writes bounded evidence for first/changed Sheet rows and exception links, classifies supported transitions, and either commits a complete current projection with canonical discovery/material updates or records a deferred projection for unresolved identity. Rejected/failed scopes roll back accepted evidence and watermark changes. For Deal OS, phase 1 inserts the durable import record and bounded accepted-row evidence in the same import transaction with one database acceptance time; rejected rows get no event. Phase 2 idempotently binds identity and projects current observations under a guarded transaction using the same event IDs and acceptance times. A phase-2 failure leaves evidence pending; status and import ID drive recovery without claiming the projection advanced. A newer accepted generation supersedes only an older pending current projection. Its accepted row evidence remains eligible for later guarded identity binding and earliest-discovery proof, even after supersession. If older accepted evidence may concern the same canonical business but cannot be proven, keep first discovery unknown instead of using the newer import as a confidently complete date. Neither phase invents a second first-discovery event. Extend SQLite admitted writers and a versioned private Postgres Sheet RPC. Resolve or disable the Postgres adapter reference to the retired per-opportunity RPC before freshness is enabled; never restore an unadmitted path. Source authority and matching rules stay unchanged.
4. Compare selected canonical evidence before and after an accepted complete projection under existing source authority rules. FL-01 material fields are asking_price, annual_profit, and annual_revenue; both sides require retained evidence IDs and the same proven metric/basis, currency, period where relevant, and canonical identity. A pre-cutover current observation without provenance is an unknown baseline; its first newly evidenced value cannot prove a rise/fall. Missing is not zero. Equal normalized value, date/timestamp refresh, formatting, owner note, or score-only write is no material change. Newly supplied value is new evidence; disagreeing sources are conflict; selected-source swap or disappearance is projection change. Append classified evidence_state_change for those and expose for research, but do not mint a material revision or claim a price rise/fall. Comparable A→B or B→A from later accepted runs is material_change, retains old/new evidence, and increments material_revision once. Disappearance never proves sale. Unknown financial semantics stay unknown.
5. Reject out-of-order runs by the generation watermark. Trustworthy source versions also reject stale source evidence; otherwise collection order means UG acceptance, not remote publication chronology. Concurrent acceptance takes one per-source lock; same-run retries cannot increment revisions twice. Deal OS phase-2 current projection checks that its import generation is latest accepted; a superseded older import cannot revert current rows but can still undergo proven identity binding for discovery. Indeterminate older identity keeps discovery unknown. Run ID, not a value hash, distinguishes a later return to a prior value.

## Reader and review contract for FL-01

SQLite and Postgres queue readers project discovery_state, first date/evidence ID, discovery_revision, latest supported current publication evidence with source/precision, actual latest accepted observation, material_revision/latest classified event, reviewed_discovery_revision, and reviewed_material_revision. Triage maps those separately for AcquisitionInbox and OpportunityDrawer; reads do not write freshness evidence. Missing publication is Age unknown. Existing incomplete history is First seen unknown — existing record. Show source health and action blockers beside last-known facts.

- **New to UG:** known_prospective, or justified known_recovered with no prior owner review of that opportunity, first accepted within the proposed 7 calendar days, and discovery_revision > reviewed_discovery_revision. Show the acceptance-date basis. Delayed identity binding does not silently make a prior review an acknowledgment: the watermark records the discovery version actually shown. A recovered old record already reviewed by an owner is Discovery evidence recovered for research, not New to UG. A supported listing 90 days old may still be New to UG when first accepted today.
- **Recently listed:** only an uncontested, supported publication date within the proposed 30 calendar days; show source/date and preserve date-only precision. It never backdates UG discovery.
- **Updated since review:** a supported `material_change` with `material_revision > reviewed_material_revision`, or an explicit unreviewed material event if no review exists. Show the changed field and old/new evidence. A source conflict or projection change is a research explanation, not a price-change badge.
- **Review acknowledgment:** existing Pursue/Watch/Pass compares expected discovery and material revisions the owner saw to the current canonical pair, then stores both with existing fingerprint/semantic digest and reviewed_at. Stale expected pair returns reload/conflict without acknowledging unseen evidence. Legacy clients lacking either expected revision keep their score-review behavior but cannot advance either freshness watermark. Existing score-review fields retain prior meaning; score-only refresh creates no Updated or New badge. Later material or discovery revision remains visible until current review acknowledges it.

The proposed fresh-first-v1 server policy uses **separate default Inbox areas over the same eligible canonical opportunities**. Needs Your Action is a compact preview of supported due broker/materials actions and deliberate urgent/high owner priorities, using existing workflow and owner-priority authority. Its proposed three distinct-row limit reserves up to two rows for due actions (overdue first, then due time) and one for owner priorities (urgent before high); unused places backfill from either set. At the supported desktop viewport, the compact area must leave the New & Important heading and at least its first discovery row visible on the initial screen; on narrower screens, compress/collapse the preview while keeping counts and View all accessible. An opportunity qualifying for both occupies one preview place and shows both reasons. Display distinct total due and owner-priority counts, including overdue/urgent counts, and visible View all actions/View all priorities links to complete server-paginated sets. Counts and links remain visible when either set exceeds the preview; the preview never implies the remaining urgent work is gone.

New & Important has its **own proposed ten-row first page** and distinct canonical-opportunity count. It queries the full eligible set for groups (1) unreviewed current high-fit (existing 75+ band), non-low-confidence New to UG **and** Recently listed, then (2) equivalent New to UG with old/unknown listing age. Older priority-only rows cannot consume this page. View all New & Important reaches the complete ordered discovery set. An adjacent Updated entry covers (3) supported Updated since review; other High Fit Needs Review (4), lower-confidence/low-fit/uncertain-source research (5), and unchanged backlog (6) remain reachable through their views and All Active. A fresh 40-fit row stays research; an old unchanged 92-fit row remains in All Active/Highest Fit and may be pinned. This changes only default presentation and independent pagination, not those freshness/fit classifications.

Each area query applies its eligibility, source-health/action blockers, filters, count, and deterministic sort to the **entire server-side result set before its own pagination**. Use one as-of instant/calendar date per request and canonical opportunity ID ascending as final tie-breaker. Within discovery groups keep explicit owner priority, supported due time where relevant, fit descending, confidence high→medium→low, and supported event time descending. All Active may retain ordinal 0 (due/owner priority) before groups 1–6 for deliberate browsing; it cannot supply the default New & Important page. Newest sorts by first accepted UG discovery (known first, unknown last), not observed_at or scored_at; Highest Fit sorts fit descending, both with canonical-ID ties. Each area has its own cursor/page and total distinct-canonical count; View all starts at that area's first page, not at an offset into another area. A cursor includes area, filters, sort, as-of basis, last comparison tuple, and a server-computed result-set revision digest of the full eligible ordered IDs/comparison tuples and distinct total; new results do not reorder an open page or discard a detail draft. Recompute that reader-only digest on continuation and, if it differs, return a stale-page signal and offer refresh instead of silently skipping/duplicating rows. Returning from detail restores area, filters, cursor/page, row anchor, and scroll context. A canonical opportunity may appear in action and discovery contexts, but both reference the same ID, decision state, and existing actions; never create a second task or add the two area counts as a unique-business total. Exclude Passed from active areas under existing disposition semantics. Do not change fit scores, acquisition/contact criteria, 72-hour export freshness, source admission, or send authority. Preserve linked CRM navigation and an honest unlinked prerequisite.

The 7/30-day windows and this comparison order are **proposed pilot parameters for the draft FL-01 implementation**, not approved outreach rules. The owner-facing “Why here?” phrase must identify the actual supported group/basis, such as “Owner priority,” “First accepted 2 days ago; listing date unknown,” or “Asking price changed since review.”

## Migration and rollout boundary

Apply additive SQLite/Postgres schema first, defaulting existing canonical rows to untracked_legacy and both reviewed-score watermarks to 0; old readers/writers continue but cannot generate freshness claims. Enable extended atomic writers for every admitted source path and review action before freshness labels/ranking. The retired Postgres per-opportunity RPC mismatch is a rollout gate, not permission to revive unadmitted mutation. If a path cannot persist provenance, fail freshness projection closed while preserving its existing source error behavior. Publication mappings need verified semantics; unsupported sources stay Age unknown. Optional recovery cites retained import/seen/alias evidence and preserves unknown when earliest proof is absent. No mandatory full historical repair, production backfill, or change to V3 immutable evidence. Proven identity correction appends lineage and re-evaluates projections without changing original event payloads or unrelated owners.

## Alternatives and decisions remaining

Using `deal_hunter_seen_deals.first_seen_at` or canonical `created_at` alone fails legacy/identity continuity. Keeping only current source observations loses history on replacement. Reusing CRM activities would omit unlinked opportunities and couple freshness to communications. A general event-sourcing system or full snapshot per import stores much more than FL-01 needs. The two narrow tables plus current-row columns preserve only accepted provenance and meaningful transitions.

**Owner decision requested:** approve this bounded durable contract and the proposed FL-01 material-field/ranking policy before implementation planning. Source-specific publication/currency/metric mappings must be evidenced during implementation; unsupported mappings remain explicitly unknown rather than guessed. No production data or live source inspection is a prerequisite to begin synthetic provider tests. The smallest later implementation sequence is schema/guarded provider writes → real provider ingestion and retry tests → read projection/review watermark → deterministic queue/UI and browser acceptance → draft runtime PR and hosted CI. Each step remains separately governed by later authorization.
