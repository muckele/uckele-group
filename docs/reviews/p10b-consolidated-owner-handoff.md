# Consolidated owner handoff (offline implementation)

This bounded change reuses the reviewed owner-operated `owner-issue-once.py`
mechanism used on October 15. That wrapper already captures original UTC times
around one creation call, inherits creator stdout/stderr in the owner's private
Terminal, and redirects only the separate public listing. The launcher never
invokes issuance, reads creator output or parses the listing. The earlier design
proposal to return to timestamp transcription was mistaken.

## Future owner journey

1. Review the existing setup scope and give recipe-bound setup consent.
2. Personally operate the separately reviewed issuance wrapper once. It captures
   original times and stages the public listing. The helper verifies the public
   row and stages the existing strict `public-token-metadata.json` import. At
   most one public-record readiness pause coordinates these steps.
3. Review one combined public-facts card and attest successful owner issuance,
   unrevoked public metadata and selection of the matching private credential.
   Its digest binds all four wrapper receipt hashes, selected metadata/hash,
   original times, recipe digest and the exact attestation meanings.
4. Enter the credential once through the existing hidden private TTY prompt.
   Actual public-input validation precedes this prompt. The existing authorized
   read-only preflight then collects fresh public observations, closes its
   clients/private context and seals the concrete session.
5. Review the concise session summary and approve the same exact session digest
   with the existing final approval phrase. The complete sealed packet remains
   available at its displayed path. Current runtime and terminal closure proceed
   unchanged only after this separate decision.

This replaces timestamp transcription and repeated ISSUED/UNREVOKED/MATCHED
confirmations. Setup consent, the combined public attestation and exact runtime
approval are three distinct decisions. Credential entry and any one readiness
pause remain separate interactions. Matching an opaque credential remains
owner-attested; public receipts do not cryptographically attest execution of the
wrapper or authenticate that credential's ID.

## Bounded public contract

A future recipe may opt in with one `ownerIssuanceDirectory` absolute canonical
path ending in `owner-public-issuance`, beneath an existing owner-only 0700
parent. No wrapper hash is embedded in the recipe. Freeze that recipe first;
the existing externally reviewed wrapper can then pin its final hash/digest, and
its own checksum is reviewed externally. This preserves the existing acyclic
binding arrangement. Historical wrapper/package/source/receipts stay immutable.
No future wrapper or live package is generated by this implementation.

The launcher reads only `intent.json`, `creator-result.json`, `list-result.json`
and `public-staging-ready.json` from that directory. It validates exact schemas,
types, positive normal/no-signal process closure, request bounds, app/name/recipe
and setup-permission hash, and setup→intent→creation→listing→current-time
chronology. Original creation times are imported without regeneration. The ready
marker's `matchingPublicRowVerified=false` and `metadataImported=false` stay false.
Selection uses the separately verified metadata import.

Directory/file reads are bounded, owner-only, nofollow/nonblocking, coherent and
rechecked after confirmation. Metadata selection, SHA and identity derive from
the same read. Only the exact absent receipt-directory leaf under a validated
unchanged parent can enter the single readiness pause. Partial/malformed/unsafe
or changed records hold; new mode never falls back to manual legacy input.
Existing consumed-attempt, freshness, source and session checks remain binding.
Recipes without the opt-in retain their existing flow; they cannot be rebound.

## Evidence boundary

Tests include actual private TTYs, the exact reviewed wrapper source snapshot
(imported only with synthetic creator/list commands), actual Node public
validation/session sealing, and real owned subprocess/private-context cleanup.
Source/native-file gates and external Machine/registry responses are explicit
fixtures; the final external runtime boundary is simulated. Tests do not replace
an entire preflight with fabricated successful output. Refusal, changed public
facts, mistaken private paste, preflight failure, final refusal and replay remain
closed. The snapshot is a non-entrypoint `.txt` fixture; no real issuer command
is run.

No runtime/shutdown, provider, approval schema or allowance changes are made.
Historical failure cause remains unknown. No live package, issuance, build,
Machine operation, provider call or email occurs; production readiness remains
false and global automation paused. A future package and execution still require
their own concrete approvals and reviewed bindings.
