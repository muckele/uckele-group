# Bounded zero-document recovery capture

`server/services/recoveryCapture.js` provides an opt-in worker core for a one-time recovery capture. It has no live-source CLI or application startup integration. The core never runs retention or opens/initializes the source; its caller supplies an already-open trusted better-sqlite3 connection. The separate `recoverySource.js` path adapter opens a read-only WAL connection under the explicit contract below. Neither has been invoked against production. Only SQLite online backup reads that source; normalization writes only the new owned copy. Existing scheduled backup creation, verification, restore, and retention remain unchanged.

Use an existing canonical directory owned by the process uid with permissions 0700. Each invocation exclusively creates a private `recovery-<uuid>` directory, constructs `bundle.incomplete`, closes SQLite and file handles, fsyncs the database, manifest, and directories, and renames to `bundle`. The result is a v2 bundle readable by the existing backup verifier/restore tooling. The published path does not use the scheduler's `backup-*` naming, so the scheduler does not adopt or prune this release recovery artifact. A failed publication after rename returns `RECOVERY_PUBLICATION_UNCERTAIN` with `publishedPath`; preserve that bundle and investigate durability rather than retry blindly. Pre-publication cleanup unlinks only known files in the newly owned unchanged directory; unexpected files/identity drift fail closed for inspection.

This helper rejects any snapshot containing a secure-document row (including differently cased table names or views). An empty or absent table is accepted. It never copies, hashes, deletes, or reads vault document contents. This restriction addresses the observed zero-document case without certifying document-copy race handling. A future nonzero-document snapshot is a stop condition.

## Limits and qualification

Defaults may only be tightened: standalone SQLite database at most 154 MiB; initial free space at least **850 MiB**; process RSS at most 256 MiB at cooperative checks; 30-second cooperative deadline. It also requires 256 MiB remaining free before publication. SQLite backup advances in 32-page batches, verification uses a 2 MiB destination cache and no mmap, and hashing reuses 64 KiB. Synchronous SQLite and fsync calls can block the event loop, so this core alone cannot provide a hard timeout or prevent transient RSS overshoot. It assumes a trusted private directory without a hostile same-uid actor replacing paths between system calls; it is not a general untrusted-upload verifier.

`node scripts/qualify-recovery-capture.js` creates a small new synthetic fixture and supervises a separate 64 MiB V8-heap worker. `--database-mib 154` generates roughly 153.5–154 MiB of SQLite data and captures a WAL-only committed row. On Linux the parent samples `/proc/<pid>/status` every 25 ms, requests termination above 256 MiB RSS, and applies a 45-second capture deadline (90-second total). SIGTERM is followed by SIGKILL after one second if needed; cleanup waits for the child close event. Sampling is evidence/termination control, not an OS-enforced memory ceiling. The runner independently checks source main/WAL hashes and the published hash, emits platform/Node/SQLite/peak RSS evidence, and deletes only its own new synthetic fixture. `--test-timeout` intentionally blocks the worker with a SIGTERM handler installed and proves SIGKILL escalation, positive exit, and cleanup. The runner exercises the path adapter against its own new synthetic WAL source and verifies source-connection closure. It has no live-source path argument; do not adapt it for production ad hoc.

Local tests use small fixtures only while Time Machine runs. The existing public-repository Ubuntu/Node 22 workflow adds a focused push job only for `codex/bounded-recovery-capture`, using locked runtime dependencies and the 154 MiB qualification plus timeout case. It does not start Docker or download browsers, add caches/artifacts, or change deployment workflows. The original full validation job remains mandatory for main pushes and other pull requests. The same-repository recovery branch also uses the focused lane while its PR is a draft; moving it to ready for review triggers the full job. Forks with the same branch name do not receive this exception. A green hosted result establishes Linux host measurements, not measurements inside the production image or the shared 1 GiB Machine. No container image is built by these new steps. The explicitly authorized draft recovery PR skips Docker/PostgreSQL and browser coverage. That skipped coverage is a release limitation. Do not mark it ready or merge under the current no-Docker/no-deployment constraint.

## Read-only path adapter contract

`captureRecoveryFromSqlitePath` in `server/services/recoverySource.js` is an exported API, with no live CLI or automatic invocation. It requires `acknowledgeWalSharedMemoryEffects: true` before any source access. The main database must be a canonical, existing WAL-mode SQLite file with existing WAL and SHM files; each must be regular, singly linked, owned by the process uid and not writable by other users. It pins source descriptors and trusted canonical source/output directory ancestry: the immediate parent must be owned by the process uid and not writable by others; ancestors must be owned by root or the process uid and cannot be writable by others except sticky directories such as `/tmp`. Private output and the 850 MiB initial space gate are checked before opening SQLite. Unsafe ancestry, missing files, identity changes and unacknowledged effects fail closed.

The adapter uses `readonly`, `fileMustExist`, `query_only`, a 2 MiB cache, no mmap and a 1-second busy timeout. It never changes source journal mode, opens application storage or runs migrations, cleanup, retention, providers or email. Source reader and every pinned file/directory descriptor close before success is reported, and caller-owned connections remain untouched. Failures after publication retain the exact artifact and report `RECOVERY_SOURCE_FINALIZATION_UNCERTAIN` plus `publishedPath`; no blind retry or cleanup is permitted.

Read-only SQLite WAL connections can update SHM read marks/locks. Concurrent SQLite writers may change the main/WAL normally; a read-only connection is not a promise of byte-identical SHM or a guarantee that a sidecar removed in a race cannot be recreated by SQLite. Stable identities are checked before opening, before capture and after capture. The adapter assumes no hostile same-uid process replacing paths between checks; pinned descriptors and trusted ancestry protect against other users, not malicious same-uid races. The synthetic harness proves main/WAL hashes stay unchanged when no concurrent writer runs. Any actual production invocation requires explicit live qualification/capture authority that names these effects.
