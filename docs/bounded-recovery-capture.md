# Bounded zero-document recovery capture

`server/services/recoveryCapture.js` provides an opt-in worker core for a one-time recovery capture. It has no live-source CLI or application startup integration. It never runs retention or opens/initializes the source. The caller supplies an already-open, trusted better-sqlite3 connection. Only SQLite online backup reads that source; normalization writes only the new owned copy. Existing scheduled backup creation, verification, restore, and retention remain unchanged.

Use an existing canonical directory owned by the process uid with permissions 0700. Each invocation exclusively creates a private `recovery-<uuid>` directory, constructs `bundle.incomplete`, closes SQLite and file handles, fsyncs the database, manifest, and directories, and renames to `bundle`. The result is a v2 bundle readable by the existing backup verifier/restore tooling. The published path does not use the scheduler's `backup-*` naming, so the scheduler does not adopt or prune this release recovery artifact. A failed publication after rename returns `RECOVERY_PUBLICATION_UNCERTAIN` with `publishedPath`; preserve that bundle and investigate durability rather than retry blindly. Pre-publication cleanup unlinks only known files in the newly owned unchanged directory; unexpected files/identity drift fail closed for inspection.

This helper rejects any snapshot containing a secure-document row (including differently cased table names or views). An empty or absent table is accepted. It never copies, hashes, deletes, or reads vault document contents. This restriction addresses the observed zero-document case without certifying document-copy race handling. A future nonzero-document snapshot is a stop condition.

## Limits and qualification

Defaults may only be tightened: standalone SQLite database at most 154 MiB; initial free space at least **850 MiB**; process RSS at most 256 MiB at cooperative checks; 30-second cooperative deadline. It also requires 256 MiB remaining free before publication. SQLite backup advances in 32-page batches, verification uses a 2 MiB destination cache and no mmap, and hashing reuses 64 KiB. Synchronous SQLite and fsync calls can block the event loop, so this core alone cannot provide a hard timeout or prevent transient RSS overshoot. It assumes a trusted private directory without a hostile same-uid actor replacing paths between system calls; it is not a general untrusted-upload verifier.

`node scripts/qualify-recovery-capture.js` creates a small new synthetic fixture and supervises a separate 64 MiB V8-heap worker. `--database-mib 154` generates roughly 153.5–154 MiB of SQLite data and captures a WAL-only committed row. On Linux the parent samples `/proc/<pid>/status` every 25 ms, requests termination above 256 MiB RSS, and applies a 45-second capture deadline (90-second total). SIGTERM is followed by SIGKILL after one second if needed; cleanup waits for the child close event. Sampling is evidence/termination control, not an OS-enforced memory ceiling. The runner independently checks source main/WAL hashes and the published hash, emits platform/Node/SQLite/peak RSS evidence, and deletes only its own new synthetic fixture. `--test-timeout` intentionally blocks the worker with a SIGTERM handler installed and proves SIGKILL escalation, positive exit, and cleanup. The runner has no live-source path argument; do not adapt it for production ad hoc.

Local tests use small fixtures only while Time Machine runs. The existing public-repository Ubuntu/Node 22 workflow adds a focused push job only for `codex/bounded-recovery-capture`, using locked runtime dependencies and the 154 MiB qualification plus timeout case. It does not start Docker or download browsers, add caches/artifacts, or change deployment workflows. The original full validation job remains mandatory for main pushes and pull requests; it is skipped only for the added development-branch push event. A green hosted result establishes Linux host measurements, not measurements inside the production image or the shared 1 GiB Machine. No container image is built by these new steps. A pull request still triggers the existing full job, including Docker/PostgreSQL and browser installation. Do not open a pull request under a blanket no-Docker/no-large-download constraint; a reviewed pushed branch provides the current deliverable.

## Capacity gate

The closed preflight recorded **563.5 MiB free**, not 850 MiB. The 850 MiB planning guard covers retaining a fresh 154 MiB recovery bundle, the next unchanged scheduled stock backup's 308 MiB duplicate staging, 128 MiB concurrent growth, 256 MiB remaining floor, and 4 MiB metadata. It assumes zero documents and both database sizes at most 154 MiB. Old backups are retained; retention happens after scheduled capture. Free space and database/document sizes must be rechecked under future bounded authority. The old provisional 26 MiB margin is insufficient.
