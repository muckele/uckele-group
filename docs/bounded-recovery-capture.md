# Bounded zero-document recovery capture

`server/services/recoveryCapture.js` provides an opt-in worker core for a one-time recovery capture. It has no live-source CLI or application startup integration. The core never runs retention or opens/initializes the source; its caller supplies an already-open trusted better-sqlite 3 connection. The separate `recoverySource.js` path adapter opens a read-only WAL connection under the contract below. Only SQLite online backup reads that source; normalization writes only the new owned copy. Existing scheduled backup creation, verification, restore, and retention remain unchanged.

Use an existing canonical directory owned by the process uid with permissions 0700 and trusted ancestry. Each invocation exclusively creates a private `recovery-<uuid>` directory, constructs `bundle.incomplete`, fsyncs the database, manifest and directories, and renames to `bundle`. The result is a v 2 bundle readable by the existing verifier/restore tooling. The published path does not use the scheduler's `backup-*` naming, so the scheduler does not adopt or prune it. A failure after rename returns `RECOVERY_PUBLICATION_UNCERTAIN` with `publishedPath`; preserve that bundle and investigate durability rather than retry blindly. Pre-publication cleanup unlinks only known files in the newly owned unchanged directory; unexpected files/identity drift fail closed for inspection.

The helper rejects any snapshot containing a secure-document row, including differently cased table names or views. An empty or absent table is accepted. It never copies, hashes, deletes or reads vault document contents. Nonzero documents require a separate implementation and review.

## Limits and synthetic qualification

Defaults may only be tightened: standalone database at most 154 MiB; initial free space at least 850 MiB; process RSS at most 256 MiB at cooperative checks;30-second cooperative deadline. It also requires 256 MiB remaining free before publication. Online backup advances in 32-page batches, verification uses a 2 MiB destination cache with no mmap, and hashing reuses 64 KiB. Synchronous SQLite and fsync calls can block the event loop; an external supervisor is required for hard termination. RSS sampling cannot guarantee zero transient overshoot.

The 850 MiB planning guard covers a 154 MiB retained recovery bundle, a subsequent unchanged stock backup's 308 MiB duplicate staging,128 MiB concurrent growth,256 MiB remaining floor and 4 MiB metadata. It assumes zero documents and both databases at most 154 MiB. Retention occurs after scheduled capture, so previous backups must fit throughout creation. Verify current free bytes and size/document assumptions at each authorized invocation; never treat a historical measurement as current authority.

`node scripts/qualify-recovery-capture.js` creates a small new synthetic fixture and supervises a separate 64 MiB V8-heap worker. `--database-mib 154` generates roughly 153.5–154 MiB of SQLite data. The runner exercises the path adapter against its own source, checks a WAL-only committed row and source-connection closure, independently verifies source main/WAL hashes and the published hash, and deletes only its newly owned synthetic fixture. It has no live-source path argument.

On Linux the parent samples `/proc/<pid>/status` every 25 ms, terminates above 256 MiB worker RSS and applies independent 90-second total/45-second capture deadlines. SIGTERM is followed by SIGKILL after one second if necessary. Cleanup waits for the child close event. `--test-timeout` blocks a worker with a SIGTERM handler installed and requires SIGKILL, positive exit and owned cleanup. Results record platform, Node, SQLite, database size, process peak RSS, `/proc` sample peak and verification outcomes.

The same-repository recovery development branch and its draft PR use focused standard Ubuntu/Node CI with locked runtime dependencies. It runs the focused tests, full-size synthetic qualification and timeout case, without Docker, browser installation, artifact uploads or caches. Other PRs and main retain full validation. Moving the recovery PR to ready for review triggers full validation. Forks with the same branch name do not receive the draft exception. Skipped Docker/PostgreSQL, browser, full-suite/build and owner-volume coverage remains a release limitation. Hosted Linux results do not establish exact-runtime/shared-Machine memory safety.

## Read-only path adapter contract

`captureRecoveryFromSqlitePath` in `server/services/recoverySource.js` is an exported API without a live CLI or automatic invocation. It requires `acknowledgeWalSharedMemoryEffects: true` before source access. The main database must be canonical and already in WAL mode, with existing WAL and SHM files. Each source file must be regular, singly linked, owned by the process uid and not writable by other users.

The adapter pins source descriptors and canonical source/output directory ancestry. Immediate parents must be owned by the process uid and not writable by others; output must also be private. Ancestors must be owned by root or the process uid and cannot be writable by others except sticky directories such as `/tmp`. Private output and the 850 MiB initial space gate are checked before SQLite opens. Unsafe ancestry, missing files, changed identities and unacknowledged effects fail closed. Both APIs assume no hostile same-uid process replacing paths between checks; they are not general untrusted-upload verifiers.

The reader uses `readonly`, `fileMustExist`, `query_only`, a 2 MiB cache, no mmap and a 1-second busy timeout. It never changes source journal mode, initializes application storage or invokes migrations, cleanup, retention, external providers or email. The source reader and every owned file/directory descriptor close before success is reported. Caller-owned connections remain untouched. A post-publication source finalization failure returns `RECOVERY_SOURCE_FINALIZATION_UNCERTAIN` with the retained `publishedPath`.

Read-only SQLite WAL connections can update SHM read marks/locks. Concurrent writers can legitimately change main/WAL contents. Read-only mode does not promise byte-identical SHM or guarantee that a sidecar removed in a race cannot be recreated by SQLite. Stable identities are checked before opening, before capture and after capture. Any actual live invocation must explicitly authorize these effects and its exact source/output paths, bounds and supervisor.

## Separate operational gates

Before any live use, independently review the invocation, qualify the exact runtime/native binding, and budget worker, supervisor, concurrent application RSS and a declared reserve. A bounded metadata-only runtime/memory preflight is distinct from a synthetic runtime qualification. Both are distinct from real recovery capture and from deployment. Neither this module nor CI results authorize those actions.

Any storage increase is a separate paid decision naming the target capacity, recurring cost and provider's no-shrink consequence. Record operational approvals, actual capacity/free-space measurements and application health in private change evidence rather than this public code document.

For a real capture, require fresh authorized size/document/automation/lease metadata, the 850 MiB free-space guard, the 154 MiB database bound, zero documents, acknowledged SHM effects, durable artifact verification and positive worker-exit checks. No application storage initialization or retention is permitted. Deployment additionally requires exact source/image digests, completed recovery evidence, rollback target and explicit restart/health scope. Account for startup cleanup and due scheduled jobs. Merge, deployment and external email/provider actions require their own authority.
